# 释锁命运纪要（焊点，当日不得翻口）

> 事故：解笼拨付成功、审计时间线绿灯，但 `cage_locks` 仍占着该笼键，
> 后来者一律争用红灯；业务停摆页面却显示成功闭环。
> 根因：解笼服务收尾事务漏释笼锁（`release_svc.py` 的 `finally` 只 `commit`，
> 未 `release`）。审计页另有读侧假象：`/api/locks` 返回 `items: []`。

## 唯一收尾侧：甲路径（本仓焊死）

**出金成败边界内必释锁占行，否则成功展示态正式零改、拒亮绿。**

- 解笼拨付与释锁共用同一事务边界：先删除 `cage_locks` 本持有者占行，
  成功删除（`rowcount == 1`）后才提交出金。
- 释锁占行删不掉（`released != 1`）→ 整笔回滚、拒写 `releases`、
  记审计动作 `release_lock_drift`、HTTP 500 返回「释锁偏航」，页面不显示成功。
- 业务校验失败（争用前已持锁后的 404/409/400）→ 同样在收尾侧删掉本持有者的占行，
  记 `release_lock_aborted`，避免残锁堵后人。
- 争用留痕 `contention_log` 独立提交：随后的 409 回滚不得把后到的争用痕一并抹掉。
- `/api/locks` 如实返回 `cage_locks`，禁止在页面上假装清空。

## 明确禁止

- **乙路径（对账绿灯随锁残留熄灭）不作为本仓收尾侧。** 它只让页面诚实，
  锁仍然泄漏、后人仍然被堵死，与「业务停摆」根因同源。不得与本仓混用。
- 禁止「影子拨付后晋升」等第三路。
- 禁止只改审计页锁列表排序来掩盖锁残留。
